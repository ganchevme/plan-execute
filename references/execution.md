# Execution mode

Use when implementing or resuming authorized work. Follow [shared project context](../SKILL.md#shared-project-context) for inputs; do not repeat planning unless evidence requires revising a contract or task.

## Execution loop

1. **Establish scope and state.** Follow the selected task/batch and frozen project preferences. If asked for the next task without a batch, complete one ready task. Inspect Git status before edits and preserve unrelated work. On resume, reconcile interrupted work using current artifacts and verification; do not restart completed work. If no plan exists, use planning mode to create the minimum records for the authorized work, without inventing an unrelated backlog. Apply the entry point’s supported-layout rule.
2. **Check readiness and claim.** Apply the lifecycle rules below. Resolve uncertainty affecting shared behavior or dependent work before implementation, using authorized bounded investigation/design work when needed. Clarify acceptance where plausible implementations would differ. A specified task with unmet prerequisites requires resolving scope; within an authorized batch, work on ready prerequisites first.
3. **Assign bounded work.** Use the worker protocol below or its local-work exception. When TDD applies, follow the planned RED/GREEN structure and establish RED evidence before implementation.
4. **Verify and review.** Apply the review and TDD rules below. Address defects and verify corrections before accepting.
5. **Record and commit.** Record concise verification, update task status and follow the commit policy below. Report a blocked commit rather than silently advancing.
6. **Continue or hand off.** Continue through the authorized task/batch until completion or progress requires user input or an external change. Report the outcome and precise remaining blockers using the entry point’s completion guidance.

## Worker protocol

Use a strong orchestrator with capable workers for bounded implementation, test authoring, documentation and focused review. Delegate by default; keep a task local when it is tiny or transferring the necessary context would cost more than completing it, stating that choice briefly when material.

Apply PROJECT.md’s frozen model policy from [settings.md](settings.md#defaults-and-choices), resolving IDs and effort against available tool controls. Worker selection does not change the current orchestrator. Select capability and supported effort by uncertainty, interacting constraints, consequence of error and verification difficulty, not task size or implementation/test labels alone. Keep ordinary and demanding assignments, including escalations, within the resolved effort ceiling; follow settings mode's rules for inherited effort and unsupported controls. Use a stronger permitted worker upfront when warranted; neither a failed attempt nor universally high effort is required. Record material selections, escalations, deviations and unsupported constraints in task evidence, including reported values needed to demonstrate an exact model/effort requirement. Do not repeat unchanged policy or add a generic note about inherited or unreported effort for every assignment; never claim unreported actual values were verified. Resolve explicit unsupported requirements without silent substitution. If suitable delegation is unavailable, disclose it and work locally only when model constraints permit.

Give each worker a bounded brief: task ID/file, objective, current capability and required change, relevant safety constraints and contract/source sections, dependency interfaces, allowed files and exclusions, local decision authority and coordination needs, verification command and expected RED/GREEN outcome when applicable. Summarize essential contracts with authoritative links; keep shared decisions and acceptance in those records, not only in messages. Include known pitfalls only when relevant. Pass the brief rather than the full conversation or all planning files when tooling permits; scale detail to uncertainty without mandatory headings. Workers return changed files, concise command/exit evidence, blockers and proposed status.

Corrections identify the violated requirement, evidence and expected behavior. When a worker stalls or corrections reveal recurring misunderstanding, reassess the contract, brief, scope, verification setup and worker capability; change the relevant input before retrying. Escalate directly when the difficulty is understood. Record newly settled shared behavior in the canonical task/contract and reconcile affected consumers. Do not repeat identical failing assignments indefinitely or attribute every failure to the worker model.

## Task lifecycle and ownership

Statuses: todo, in_progress, done, blocked, cancelled. A ready todo task requires completed prerequisite rows and the required interfaces/evidence; missing or cancelled prerequisites do not count as done. Claim ready work as in_progress; mark it done only after acceptance, or blocked with an actionable reason when progress cannot continue. Never mark unfinished work done to end a session; no ready tasks does not mean the project is complete.

Keep the same status in each task file and TASKS.md, synchronizing on a best-effort basis at transitions and before ending a turn. Reconcile interrupted inconsistencies from artifacts/evidence rather than assuming success. Keep current verification in task files, not copied log transcripts. Do not duplicate status tables in component guides; routine completion updates the task record and register, not PROJECT.md.

The orchestrator owns acceptance, integration, shared task status and commits unless explicitly delegated. Maintain one owner per editable file; do not take actively owned work. Workers must not independently change shared contracts or race on the register. A shared architecture owner resolves cross-component changes. Concurrency follows the frozen preference: sequential delegation is valid, while parallel work requires ready tasks, stable interfaces and disjoint file ownership. Use isolated worktrees where useful, then integrate and verify before dependent work starts.

## Context and review

Begin implementation review with task acceptance criteria, changed-file summary, scoped diff and concise verification. Inspect Git status so new/untracked files and pre-existing changes are accounted for; ordinary `git diff` omits untracked files. Include new-file content in review and choose a base that covers the actual task changes. Expand into surrounding code, callers, contracts and affected tests when needed to assess correctness, safety or integration. Diff-first is a starting point, not a limit on review depth. A cross-project architecture review may require broader context from the outset.

Run prescribed checks or assess trustworthy evidence tied to the exact integrated changes; repeat checks when integration, edits or uncertainty invalidate it. Match evidence to the claim being accepted: check that tests and fixtures exercise the relevant behavior and could detect its important failure modes. For environment, configuration or execution-path claims, confirm the check actually exercised them; command success alone may not establish that. Use a targeted negative control or environment/artifact inspection when it resolves a material doubt. Do not impose mutation testing, extra review rounds or broader reruns without a concrete verification need.

Review substantial layers, dependencies and operating mechanisms introduced during implementation against the task's outcome, use cases and constraints. When a materially simpler approach preserves them, identify the reduced burden and verify the simplification; retain complexity justified by security, recovery, compatibility or established contracts. If a finding questions an explicit requirement, apply the requirements review in [planning.md](planning.md) and explain the tradeoff before seeking the user's decision. Keep unrelated settled decisions outside the review. Use an independent reviewer when consequential judgment adds value; no mandatory extra agent or review artifact for tiny changes.

## TDD

When the resolved `workflow.tdd` setting is enabled, new behavior follows RED then GREEN using the task structure chosen during planning. RED defines contract tests plus minimal importable stubs and demonstrates failure at the intended behavioral assertion before implementation. Missing dependencies, collection errors and broken fixtures are not RED. GREEN implements the contract and passes focused checks plus affected predecessor tests. Do not weaken established assertions, skip failures or rewrite expected output to match implementation. The orchestrator may correct a demonstrated test defect, explaining it and reestablishing meaningful evidence; no automatic human-approval ceremony for every test correction.

For a combined task, record RED evidence before GREEN and keep the task in_progress until GREEN verification passes. For separate tasks, accept RED on intended assertion-failure evidence and make GREEN depend on it; a completed RED task is intentionally not a green suite. Existing explicit task contracts remain binding unless deliberately revised.

When TDD is disabled, implement and verify against the task’s acceptance criteria, including meaningful behavioral tests; do not manufacture a RED phase or weaken established tests.

Setup, docs, packaging acceptance and previously implemented behavior can pass immediately; never break working code just to manufacture RED. Default tests use synthetic fixtures/fakes. Live checks are explicit, bounded and authorized. Include final integration checks and early vertical slices for large projects. Full suite repetition is warranted at integration or when a change has broad effects, not after every trivial edit.

## Logs and wrapper

Append to existing logs using append mode; do not read the whole log merely to add an entry and rewrite the file. Command output can instead go to a fresh unique raw-output file. Preserve existing log content; never truncate, rotate or delete logs as a convenience. Reading current or earlier logs is allowed when useful for diagnosis, review or a current task question; prefer relevant excerpts. Keep secrets/private content out of ordinary logs and fixtures.

Follow the frozen `logging.wrapper` setting within applicable instructions and permissions. The default, `none`, uses direct capture without wrapper discovery. Otherwise use an existing external executable only when it is usable and permitted: `auto` checks PATH for `logs-wrapper`; an explicit path selects that wrapper. This skill includes no wrapper binaries or profiles. Read [logs-wrapper.md](logs-wrapper.md) only when the user requests installation or when selecting, invoking, configuring or troubleshooting a permitted wrapper. Do not install, download, copy or rebuild a wrapper automatically. An explicit user request can authorize installation from the supplied source or release location, subject to environment policy and host permissions; do not request permission again when the action is already authorized.

When the optional wrapper is absent, unusable, disallowed or unsuitable for the command, use direct capture; give a short notice if an explicit path could not be used. Capture stdout/stderr to a fresh exclusive log, preserve the child exit status and return concise evidence with the absolute raw-log path. Do not filter away the only failure evidence or unfamiliar diagnostics. An optional wrapper never blocks development. If a separate applicable instruction makes a wrapper mandatory, resolve that conflict before dependent execution rather than silently waiving it.

## Concise test evidence

Start with the command/scope, exit status, pass/fail/error counts, failing test IDs and a short explanation of the relevant assertion. During RED, confirm the observed expected-versus-actual behavior fails for the intended contract reason. A nonzero exit or a failing-test name alone is insufficient; collection/setup errors and unrelated regressions do not establish RED. If a summary cannot distinguish the cause, inspect bounded excerpts of that run's fresh log before accepting it.

Keep complete diagnostic output in the unique raw log while returning concise evidence to the agent. Prefer supported runner/wrapper summary controls that preserve diagnostics in that log. For pytest, `--tb=short` can be useful when full tracebacks are unnecessary; do not use `--tb=no` or output caps as a substitute for examining assertion evidence. If full traces must be retained, capture them in the raw log and summarize afterward instead of suppressing them at the runner. Never blindly truncate unfamiliar errors, filter away failure categories or lose the child exit status. Retrieve detailed traces only when the summary is insufficient or failures are unexpected. Task records and review handoffs contain concise evidence and the log path, not pasted stacks. Keep the same concise-first approach for GREEN and integration, expanding diagnosis as needed.

## Slow work

Use tracked background processes or event-driven completion. Continue independent ready work; otherwise use tool-supported blocking waits rather than repeated reasoning/status calls. Respect tool time limits and user-update requirements. When polling is unavoidable, use a sparse cadence suitable for the operation (often minutes), not seconds. Track process IDs/deadlines; do not start duplicate jobs because a request is quiet. Application retry/backoff belongs in application code, not agent polling loops.

## Commits

Use the commit preference recorded in PROJECT.md. Announce its default and opt-out when first resolving it; do not re-ask at each task or resume. After accepting each task, synchronize statuses, review the diff and stage only its changes and required status updates. Commit locally with task ID and concrete outcome. A separate RED task may commit with its expected assertion failures; GREEN and combined tasks commit after required passing checks. Commit before proceeding to the next sequential task; parallel integrations retain separate coherent task commits where practical.

Do not create a repository, push, amend history or commit someone else's changes by implication. If Git is absent or identity/hooks/permissions block a commit, preserve work and report the limitation; do not invent identity, disable hooks or change global Git settings. Never commit secrets, logs, virtual environments or private runtime artifacts. Report hashes in the final response, not self-referential task-file amendments.
