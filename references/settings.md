# Optional settings

These settings files are defined by this skill and interpreted by the agent; they are separate from the host app's native configuration. Neither is required:

- Personal: `~/.config/plan-execute/settings.toml`
- Project: `<project>/plan/settings.toml`

`~` means the current user's home directory. These locations are skill conventions; executable and virtual-environment paths must be resolved for the actual machine and project.

When initializing a project or resolving missing required settings, use explicit user instructions, applicable project rules, project settings, personal settings, then defaults. Merge tables by key; arrays replace rather than append. Unknown keys or invalid values should be reported, not silently treated as effective. Resolve relative executable paths against the settings file that supplied them, not the current working directory. Record resolved values and provenance in PROJECT.md; future task execution and additional planning use that frozen plan. Extending the task register does not re-resolve settled settings or repeat the commit-preference announcement. Changing personal defaults does not silently change an ongoing project's plan. User-requested changes require updating the plan deliberately.

`assets/settings.example.toml` documents supported keys and defaults. Do not create personal/project settings automatically when unnecessary. Never store API keys, private notes or credentials in either file. A user's environment preferences do not become obligations for everyone sharing the skill.

## Defaults and choices

- `models.preferred_pairs`: logical strong/default-worker role pairs, default `["sol/terra", "opus/sonnet"]`. These are preferences, not literal API model IDs. The second role is the ordinary worker preference; the first may also serve as a stronger worker when permitted. Inspect available tools/model choices when delegating. The user may choose an equivalent strong/mid-tier pairing.
- `models.excluded_workers`: default `["luna", "haiku"]`, case-insensitive family exclusions; do not silently choose an excluded worker. If no suitable worker exists, work locally or disclose the blocker rather than lowering the requested tier.
- `models.max_worker_effort`: default `"high"`. A reasoning-effort ceiling for ordinary workers, demanding workers and escalations; choose an appropriate supported level up to that ceiling, not always the ceiling itself. Use the selected model/tool's supported effort levels and ordering; report unsupported values rather than inventing an equivalent. `"unlimited"` removes the ceiling. This setting does not change the current orchestrator's effort.
- `models.worker_effort`: default `"inherit"`, with no fixed requested level. Otherwise, a reasoning-effort value supported by the selected worker and delegation tool. Both choices remain subject to `max_worker_effort`.
- `models.demanding_worker`: `"strong"` (default) or `"default"`. Strong permits the selected pair's strong role for demanding work, including initial assignment and escalation; default retains the ordinary worker preference. Explicit model restrictions and exclusions still apply. Route by the judgment and verification difficulty described in execution mode, not task size alone.
- `models.demanding_effort`: default `"inherit"`; otherwise a value supported by the selected worker/tool. This is the effort preference for demanding assignments, independently of whether the model changes, and remains subject to `max_worker_effort`. Inherit does not copy `worker_effort`. Choose an explicit value when a repeatable effort level is desired. These effort settings govern delegated workers, not the current orchestrator.
- `workflow.tdd`: default true for new application behavior. The planner chooses RED/GREEN phases within one task or separate tasks under [planning mode](planning.md#produce-executable-tasks); tests-first verification applies in either structure. Other task types have appropriate verification.
- `workflow.parallelism`: `opportunistic` (default) or `sequential`. Controls concurrency, not whether work is delegated. Sequential execution may still use one worker at a time; no requirement to fill agent slots.
- `workflow.commit_after_task`: default true. Announce early: “Local commits after each completed task are enabled; you can disable them.” An explicit request to implement under this skill uses that default without per-commit questions. Existing instructions can disable it. Planning-only invocations do not start task commits or sweep untracked files into a baseline commit.
- `environment.isolation`: `project-local` (default), `container`, or `project-policy`. The last option follows existing project conventions; it does not itself authorize unrelated OS changes.
- `environment.host_installations`: `forbidden` (default) or `allowed`. Allowed covers necessary task dependencies, not arbitrary host modification; obey platform permissions. Never infer this from using a container runtime.
- `environment.python_environment`: `venv` (default) or `project-policy`.
- `environment.container_runtime`: `auto`, `docker`, `podman`, `nerdctl`, or `none`. Discover the actual CLI/context; Rancher-managed installations may expose different interfaces. Do not install a runtime just because auto-detection failed.
- `logging.wrapper`: `none` (default), `auto`, or an executable path. `none` uses direct capture without wrapper discovery. When permitted by applicable user/project rules, `auto` checks PATH for an independently installed `logs-wrapper`; an explicit path selects that executable. This skill includes no wrapper binaries or profiles. Use direct capture if the wrapper is unavailable or disallowed; installation, download or building requires an explicit user request and applicable environment permissions. Existing permission suffices without per-use approval. See [logs-wrapper.md](logs-wrapper.md) for purpose, selection and invocation.

With a finite ceiling, leave inherited effort unspecified only when the host establishes that its effective default is within the limit; otherwise explicitly select a supported level within it. If an exact effort preference exceeds the resolved ceiling, report and resolve the configuration conflict before delegation rather than silently clamping it or exceeding the limit. If the host cannot enforce or establish the ceiling, report the unsupported constraint and follow execution mode's local-work/blocker fallback; do not claim compliance. With `"unlimited"`, inherit leaves effort unspecified without asserting an effective level.

Resolve and freeze routing/effort preferences, including the effort ceiling, when initializing project planning or for an explicitly requested settings update. Record the compact resolved model policy and provenance once in PROJECT.md; task evidence records material assignment choices and exceptions under [execution mode](execution.md#worker-protocol), rather than repeating unchanged policy. An existing frozen plan without these optional keys retains its recorded routing and leaves unspecified effort inherited; missing new keys alone do not trigger re-resolution from changed personal or skill defaults. In particular, a missing `max_worker_effort` does not add the new default ceiling to an existing frozen plan; apply it only on a deliberate settings update. Preserve existing permissions to escalate within the resolved policy. Requested settings remain distinct from tool-reported actual values; never claim an unreported model or effort was verified.

An environment with Docker available may run build tooling in containers; one without it may use project-local tooling. Respect language-specific mechanisms and the resolved `environment.python_environment` setting. When host installation is forbidden, newly installed Python packages/tools must stay in the configured project environment or another permitted isolated environment; its directory need not be named `.venv`. An existing suitable Python interpreter can run the standard-library plan validator without installing packages, subject to applicable project rules. If needed native tooling is unavailable, report that limitation rather than claim a container verifies a native integration.

A user's strict profile can keep the defaults above. A collaborator who permits necessary host installs can set `host_installations = "allowed"` and choose their project conventions. Do not ask about isolation repeatedly once the resolved policy is recorded.
